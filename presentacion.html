¿Qué hemos construido?

  • Una aplicación Todo List en React.
  • Con una suite de pruebas automatizadas usando Jest + React Testing Library.
  • Cubriendo los 4 niveles de testing:
    • Unitarias
    • Snapshot
    • Integración
    • Aceptación

Configuración de Jest + Babel

"scripts": { "test": "jest" },
"jest": {
  "testEnvironment": "jsdom",
  "setupFilesAfterEnv": ["<rootDir>/jest.setup.js"]
},
"babel": {
  "presets": ["@babel/preset-env", "@babel/preset-react"]
}
  • jsdom simula el navegador en Node.
  • jest.setup.js carga @testing-library/jest-dom para matchers como toBeInTheDocument() y toHaveClass().

Pruebas unitarias — TodoItem

test('Muestra la tarea correctamente', () => {
  render(<TodoItem task="Aprender Jest" />);
  const taskElement = screen.getByText(/Aprender Jest/i);
  expect(taskElement).toBeInTheDocument();
});

Qué valida

  • Que el componente renderiza el texto recibido por props.
  • Aísla el componente: no depende de TodoApp ni de TodoList.

Pruebas de snapshot — TodoList

test('Genera un snapshot del componente TodoList', () => {
  const tasks = ['Tarea 1', 'Tarea 2'];
  const { asFragment } = render(<TodoList tasks={tasks} />);
  expect(asFragment()).toMatchSnapshot();
});

Qué valida

  • Captura la estructura del DOM y la compara con la anterior.
  • Detecta cambios visuales no intencionados.
  • Si el cambio es intencionado: npx jest -u regenera el snapshot.

Pruebas de integración — TodoApp

test('Permite agregar una tarea a la lista', () => {
  render(<TodoApp />);
  fireEvent.change(screen.getByRole('textbox'), {
    target: { value: 'Nueva tarea' }
  });
  fireEvent.click(screen.getByRole('button', { name: /agregar tarea/i }));
  expect(screen.getByText(/nueva tarea/i)).toBeInTheDocument();
});

Qué valida

  • La interacción entre TodoApp, TodoList y TodoItem.
  • Simula escribir + pulsar "Agregar".

Pruebas de aceptación — flujo completo

// 1) agregar
fireEvent.change(input, { target: { value: 'Tarea importante' } });
fireEvent.click(button);

// 2) completar
fireEvent.click(task);
expect(task).toHaveClass('completed');

// 3) eliminar
fireEvent.click(screen.getByRole('button', { name: /eliminar/i }));
expect(screen.queryByText(/tarea importante/i)).not.toBeInTheDocument();

Qué valida

  • El flujo real del usuario: agregar → completar → eliminar.

Decisiones arquitectónicas

  • Separación de responsabilidades:
    • TodoApp = estado y lógica
    • TodoList = presentación
    • TodoItem = presentación + estado local completed
  • Inmutabilidad: setTasks([...tasks, ...]) y filter(...), nunca mutar el array.
  • Comunicación padre-hijo por props y callbacks (onDelete).
  • MVC de facto: modelo = tasks, vista = TodoList/TodoItem, controlador = TodoApp.

Conclusiones

  • La app queda verificada por 4 tipos de pruebas que cubren desde un componente aislado hasta el flujo completo del usuario.
  • Jest + RTL dan un feedback rápido y fiable.
  • El diseño por componentes + inmutabilidad facilita añadir funcionalidades (editar, filtrar, persistir).
